# Dagger CI / performance comparison

An opt-in companion to GitHub Actions, not a replacement. No existing workflow
changes, GitHub token, Dagger Cloud account, or externally hosted database is
required. Run from the repository root with Docker running and **Dagger
v0.21.11** installed. The engine/SDK version is pinned in `dagger.json`; application
containers use Node **26.5.1** and the repository's Yarn **4.18.1** release.
Image tags, unlike digests, can be republished: record resolved images when
publishing performance comparisons.

Node uses system CA certificates in addition to its built-in roots. For networks
with a TLS proxy, install the operator's CA through Dagger's
[custom CA configuration](https://docs.dagger.io/reference/configuration/custom-ca).
Certificate checks remain enabled.

## Run

```sh
docker info
dagger -m .dagger develop
dagger -m .dagger functions
dagger -m .dagger call smoke
dagger -m .dagger call services-smoke
dagger -m .dagger call plan --pipelines=server --tasks=test
dagger -m .dagger call check --source=. --pipelines=shared
dagger -m .dagger call check --source=. --pipelines=front,server --tasks=lint,typecheck --concurrency=2
dagger -m .dagger call check --source=. --pipelines=all
dagger -m .dagger call check --source=. --pipelines=front --tasks=storybook
dagger -m .dagger call artifact --source=. --pipeline=front export --path=.dagger/results/front
dagger -m .dagger call artifact --source=. --pipeline=ui --storybook export --path=.dagger/results/ui-storybook
```

`--pipelines` accepts `shared,ui,front,server,sdk,cli,client-sdk`, or `all`.
The default is `shared`; defaults include that package's checks and build.
`--tasks` selects a subset, rejects unsupported names, and never executes arbitrary
shell input. `plan` prints the selected check commands as JSON, without installing
the monorepo. It excludes common preparation: immutable install, shared build,
front/server `reset:env`, SDK build, and CLI+SDK builds.

Independent checks fork from immutable container snapshots and execute concurrently
(default 3, maximum 16). The Yarn download cache is shared, but `node_modules` is
an immutable install layer keyed by workspace manifests, lockfile, Yarn release,
patches, constraints and image. Only then is source overlaid. Shared build and
preparation layers are deduplicated by Dagger; Nx still supplies dependency order
but its task-result cache and Nx Cloud are disabled. This avoids stale Nx passes
and lets benchmarks measure Dagger's own reuse. Host `node_modules`, build outputs,
`.git`, caches and environment overrides are excluded. Only `.env.example` and
`.env.test` fixtures are retained. Nothing is written back unless explicitly
exported. SDK bindings generated by `develop` are ignored.

### Frozen PR checkouts without Dagger files

The module and tested source are independent. Keep this branch checked out once
and pass any frozen PR checkout as a Directory argument; that checkout needs no
`.dagger` files and is never edited:

```sh
dagger -m /path/to/dagger-branch/.dagger call check \
  --source=/path/to/frozen-pr-checkout --pipelines=sdk
dagger -m /path/to/dagger-branch/.dagger call integration \
  --source=/path/to/frozen-pr-checkout --shards=16 --shard=5
python3 /path/to/dagger-branch/.dagger/benchmark.py \
  --source=/path/to/frozen-pr-checkout --pipeline sdk --runs 3
```

The frozen commit IDs, patch IDs and source PRs are in
[`benchmarks/upstream-prs.json`](../benchmarks/upstream-prs.json).

For the fork's exact-patch examples based on `fbaaaae4aab28db62a23ae17c5dc279d2c810cce`:

| Fork PR | Upstream patch | Selection |
| --- | --- | --- |
| `nebuk89/twenty#1` | `twentyhq/twenty#29176` | `--pipelines=shared` |
| `nebuk89/twenty#2` | `twentyhq/twenty#29177` | `--pipelines=front` |
| `nebuk89/twenty#3` | `twentyhq/twenty#29349` | `--pipelines=sdk` |

Use the same module revision and frozen PR SHA for repeated measurements.
`benchmark.py` records the source commit/dirty flag separately from the module
commit/dirty flag. Outputs are written under the module checkout, not the PR.
Do not fetch full upstream history just to run these checks; a shallow frozen
checkout is sufficient because package selection does not use Git history.

## Database integration

```sh
# Full suite in one isolated service group; secure-deployment suite follows.
dagger -m .dagger call integration --source=.
# Actions-sized split, running only shard 5 on this machine.
dagger -m .dagger call integration --source=. --shards=16 --shard=5
# Run four shards concurrently, each with its own PostgreSQL/Redis/ClickHouse.
dagger -m .dagger call integration --source=. --shards=4
```

Each shard has fresh PostgreSQL 18 (`test` database), Redis 7.4 and ClickHouse
25.8.8 services, no host ports or persistent database volumes. Dagger waits for
service ports. The server is built once; each shard writes test-only service URLs
and mock billing settings into the **server** `.env.test` (dotenv overrides
environment variables), applies ClickHouse migrations, resets/seeds PostgreSQL,
and runs the existing Jest integration target. Reset runs before Jest rather
than racing it in a host background shell. Secure-deployment tests run only
after shard 1, unless `--secure=false`. Supplying `--shard` runs only that shard;
it is not a full-suite result. No Stripe credentials or real billing calls
are configured.

Start with one shard. Server tasks can allocate 6–12 GiB apiece; running 16 shards
on one Docker host is **not** equivalent to Actions' 16 separate runners.
Integration failures propagate nonzero. Package checks finish their selected
jobs and aggregate failures; integration fails on the first rejected shard.

## Benchmark

```sh
# Rerun checks, retaining immutable install/shared/preparation build layers.
python3 .dagger/benchmark.py --pipeline shared --tasks lint,typecheck --runs 3
# Measure complete Dagger graph/result replay (includes CLI/module overhead).
python3 .dagger/benchmark.py --pipeline shared --mode replay --runs 3
# Fresh Yarn cache and install layer on every run; NOT a cold engine/image cache.
python3 .dagger/benchmark.py --pipeline shared --mode fresh-deps --runs 3
# Compare the same integration shard on multiple PR worktrees.
python3 .dagger/benchmark.py --integration --shards 16 --shard 5 --runs 3
```

`--dagger /path/to/dagger` selects the CLI. Each run appends JSONL to
`.dagger/results/benchmarks.jsonl`, including commit, dirty flag, CLI version,
exact argv, wall seconds, exit status, parsed successful result and stdout/stderr
paths. It exits nonzero if any run fails. Logs remain local. The JSON inside
`check` measures job intervals including shared dependency waits, not isolated
CPU time. **Use outer `wall_seconds` for comparisons**: cached function results
contain timings from their original execution.
Each invocation has a 3600-second timeout (`--timeout-seconds` overrides it);
timeouts are recorded with exit code 124.

`checks` supplies a unique execution ID after preparation so checks actually
rerun; `replay` permits complete result reuse; `fresh-deps` additionally chooses
a unique download-cache namespace, invalidating the install and descendant
layers. Warm builds may still be reused in `checks`. For a genuinely cold
engine, provision a separate disposable Docker host/engine; never prune a shared
developer engine. Use the same commit, source state, task selection, shard count,
CPU/memory limits, architecture and cache policy on both systems. Compare against
the corresponding Actions job(s), not aggregate wall time of unrelated workflows.
Some Actions jobs request `ubuntu-latest-8-cores`, which may not be available in
forks. These commands do **not** match or enforce those runner resources. Queued,
unavailable, skipped, or failing fork jobs are not valid full-workflow baselines.
There is deliberately no affected/changed-files gate: explicit package selection
keeps benchmark workloads stable across PRs. Actions' timings-based integration
balancer is not fetched, so shard contents can differ from a timings-enabled
Actions run; use whole-suite comparisons or the same timing inputs externally.

## Outcome parity

This table describes implemented commands, **not a claim that full suites have
been executed here**. All packages are explicitly selected, not Nx affected/tag
filtered. `all` includes the seven package pipelines, not integration or optional
Storybook builds.

| Actions source | Dagger coverage | Remaining differences/exclusions |
| --- | --- | --- |
| `actions/yarn-install` | Immutable hardened Yarn install, scripts disabled, `--check-cache`, shared dependency download cache | No Actions node_modules/cache transport; exact Node patch pinned instead of floating `26` |
| `ci-shared.yaml` | `shared`: lint, typecheck, CI unit tests; shared build prerequisites | Workflow `scope:shared` can also select UI; use `shared,ui` for both |
| `ci-ui.yaml` | `ui`: lint + `generate:check`, typecheck, unit/ownership/export tests via Nx, size, pack-size, `test:package`, build; optional `storybook` build | Browser Storybook tests, screenshots/Argos and GitHub artifact uploads excluded |
| `ci-front.yaml` | `front`: reset env, lint, typecheck, 3 CI unit shards, ordered Lingui extract/compile, production build; optional `storybook` build | Browser Storybook module/page/performance matrices, renderer tests, screenshot uploads excluded |
| `ci-server.yaml` | `server`: shared prerequisites, reset env, lint, typecheck, ordered Lingui extract/compile, 4 `test:ci` shards, server build | Running-server/worker smoke, pending migration/GraphQL code-generation checks, upgrade mutation guard and public-app jobs excluded |
| `ci-server-integration-test.yaml` | `integration`: build, PostgreSQL/Redis/ClickHouse, migrations + seeded reset, all integration shards, secure suite on shard 1 | No GitHub timing-artifact fetch/upload or timing recorder; reset is sequential; Redis pinned rather than untagged |
| `ci-sdk.yaml` | `sdk`: SDK build, lint, typecheck, `test:unit` | No change gating; build is also available as a selected task |
| `ci-client-sdk.yaml` | `client-sdk`: lint, typecheck, CI tests and build | No change gating |
| `ci-cli.yaml` | `cli`: CLI+SDK build, lint, direct `tsgo --noEmit`, unit tests with fixture isolation/worker counts, package tests | Privileged network-namespace/local-registry publishing and server-backed app lifecycle E2E excluded |
| Other workflows | None | Email/website/Zapier/companion/renderer/docs/utils/agent-skills/app checks, browser E2E/QA scout, Docker Compose/cross-version upgrades, image builds, publishing/deployment/release, translations/catalog sync, policy/approval checks, Danger/comments, preview environments and secret/host-dependent tasks remain in Actions |

Build artifacts can be exported using `artifact`; package test reports and
screenshots are not uploaded to GitHub. Generated translations stay in container
snapshots; repository catalogs are not changed.

### Implementation validation / current host limits

The following checks were executed on this worktree:

```sh
docker info --format '{{.ServerVersion}}' # 29.1.3, already running
npm --prefix .dagger ci --ignore-scripts --no-audit --no-fund
npm --prefix .dagger run typecheck
npm --prefix .dagger test # six passing selection/sharding/install-input tests
python3 .dagger/benchmark.py --help
git diff --check
```

With the downloaded pinned CLI at `.dagger/.tools/dagger`, and
`DAGGER_NO_NAG=1 _EXPERIMENTAL_DAGGER_RUNNER_HOST=docker-container://twenty-dagger-no-masq-engine`:

```sh
.dagger/.tools/dagger --progress=plain -m .dagger develop
.dagger/.tools/dagger --progress=plain -m .dagger functions
.dagger/.tools/dagger --progress=plain -m .dagger call plan --pipelines=server --tasks=test
.dagger/.tools/dagger --progress=plain -m .dagger call plan --pipelines=all # 38 jobs
.dagger/.tools/dagger --progress=plain -m .dagger call smoke # v26.5.1
python3 .dagger/benchmark.py --dagger=.dagger/.tools/dagger \
  --source=/path/to/frozen-pr-checkout --pipeline=unknown --runs=1 \
  --output=.dagger/.tools/benchmark-negative.jsonl
```

The intentional invalid-pipeline invocation used a separate clean frozen
source checkout, wrote JSONL/logs and returned a nonzero result, without
starting application suites.

The default Dagger engine could not start on this host: legacy iptables comment
matches were unsupported, and the native-nftables workaround lacked `inet` NAT
support. An isolated engine with custom CNI and IP-only NAT allowed module
generation, schema execution and the real Node container smoke above. That
workaround is **not part of this module** or a deployment requirement on normal
Docker hosts. `call services-smoke` started all three database service processes
but timed out after 150 seconds because the custom engine could not resolve
service hostnames (`server misbehaving`).

On 2026-11-02, a new Docker 29.1.3 sandbox reproduced the default-engine
failure. The pinned v0.21.11 CLI passed its published SHA-256 checksum.
Both iptables backends rejected the `comment` match, and native nftables rejected
the `inet` family. An isolated engine then started with a local compatibility
shim that removes only `-m comment --comment ...` metadata. The shim retains
traffic matches, targets and policies, including Dagger's standard CNI firewall
plugin and NAT rules. `call smoke` passed with Node v26.5.1. This is a local
diagnostic workaround, not a supported Dagger configuration.

On that engine, `call services-smoke` timed out after 180 seconds. All three
service names appeared in dnsmasq's hosts file, but lookups through `10.87.0.1`
returned `no such host`. A later trace enabled query logs on the same dnsmasq
configuration. The resolver loaded all three service names, but received zero
queries during a 65-second service check. A resolver reload did not help.
These results narrow the failure to the DNS path before dnsmasq, not missing
service registrations. The sandbox's eBPF log shows DNS redirection, but no
explicit deny event for these attempts. The current policy uses block-list
mode, unlike the earlier allowlist environment. No sandbox firewall controls
changed.

The first frozen PR #1 workload attempt failed during dependency installation
with `self-signed certificate in certificate chain`. A separate Node HTTPS
probe passed after enabling `NODE_USE_SYSTEM_CA=1`, which lets Node use the
proxy CA certificates that Dagger installs. The module now sets that option
without disabling certificate checks. The failed workload took 34.48 seconds;
it is a failure record, not a successful benchmark.

The next attempt passed TLS checks and downloaded 4,065 packages, but dependency
linking failed with `ENOSPC` after 310.62 seconds. Yarn's global cache default
overrode `YARN_CACHE_FOLDER`, so packages went into the container's filesystem
instead of the mounted download cache. The module now sets
`YARN_ENABLE_GLOBAL_CACHE=false` to use `/yarn-cache`. This sandbox has a
28 GiB filesystem; it is not an unlimited-storage runner.

A retry with the corrected mounted cache and concurrency 1 also failed with
`ENOSPC` during dependency linking after 386.53 seconds. The cache placement fix
does not solve the filesystem capacity limit. Yarn reports `/yarn-cache` as its
effective cache directory with the new settings. No application checks ran.
The frozen PR #1 checkout remains clean at
`08ebed710e0c3b270d2aab4a1fad43f336f6a24f`.

Earlier checks on the previous host found an explicit sandbox firewall restriction, not a missing
database DNS entry. During a live retry, the CNI hosts file contained all three
service names. The sandbox redirected DNS requests to its own proxy instead of
Dagger's resolver. Its firewall log recorded `DNS BLOCKED`,
`because: NotInAllowList` for the generated `*.dagger.local` names. Direct local
connection probes also recorded `PACKET BLOCKED`, `because: IPNotAllowed` for
`10.87.0.1`. A narrower NAT rule did not correct the failure; that diagnostic
change was restored.

The sandbox operator needs to approve access to Dagger's local service network
(`10.87.0.0/16` in this engine) and preserve local resolution of
`*.dagger.local` through Dagger's resolver (`10.87.0.1`). A domain allowlist
entry alone is insufficient if the sandbox still sends those private names
to an external resolver. Do not disable or bypass the sandbox firewall.
After the operator changes the supported sandbox configuration, run
`call services-smoke` before integration tests. Kernel networking compatibility
and sandbox firewall policy are separate constraints.

Database queries/full integration parity remain unverified on this host.
Application dependency installation was attempted, but no application checks
completed successfully. No performance conclusions are claimed from these
failed attempts or smoke checks.
